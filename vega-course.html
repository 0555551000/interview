Module 01

Vega 是什么

包名 com.yuewen.openplatform.vega，是阅文漫剧运营 B 端后台。和 Nova（UP 主 C 端）、Comic Drama Web（分销商 B 端）构成漫剧业务三端。

🎬运营小张的一天

  • 早上 9 点 → 打开 Vega 后台 → 看 ContractMonitorJob 凌晨跑的"超时未签合同"报告
  • 10 点 → 上游推来批量脚本 Excel → FileTaskJob 自动解析 → 审核
  • 下午 → 审核非标视频（NonStandardVideoService）→ 打上 CAMS 标签
  • 傍晚 → 合同 OA 回调过来 → ContractController.callback 验签 → 更新状态
💡
Vega 的特征（和 Nova 对比）

• 50 Service、39 Manager、11 Job：体量大，业务逻辑复杂。
• Spring Security + 角色权限：B 端运营人员多，需精细权限控制。
• XXL-Job 定时任务：大量后台批处理（合同监控、文件处理、全量同步）。
• Excel 文件流水线：结算单/数据采集都要解析 Excel。
• 合同 OA 回调 + HMAC 签名：外部合同系统回调验签。

Module 02

Filter + Spring Security 权限

Vega 的 BasicFilter 和 Nova 一模一样（阅文框架共用），这里重点看 Spring Security 的 UserDetailsService 接入。

🔐CustomUserDetailsService 真实代码

Javaservice/CustomUserDetailsService.java（完整）
@Service
public class CustomUserDetailsService implements UserDetailsService {

    @Resource
    private AuthorizationManager authorizationManager;

    @Override
    public UserDetails loadUserByUsername(String username) {
        // ⭐ 注意:username 参数实际不用,用的是 SessionContext 里的 userId
        long userId = SessionContext.getSessionValueOrException(SessionContext::getUserId);

        User userInfo = authorizationManager.getUserInfo(userId);
        if (userInfo == null) {
            throw new BusinessException(ErrorCode.USER_NOT_EXIST);
        }

        // 拉取角色 + 细粒度权限(多对多)
        List<PermissionDO> userAuthorities = authorizationManager.getUserAuthorities(userInfo.getUserId());

        List<GrantedAuthority> authorities = new ArrayList<>();

        // ⭐ 角色必须加 ROLE_ 前缀（Spring Security 约定）
        userInfo.getRoles().forEach(role -> {
            authorities.add(new SimpleGrantedAuthority("ROLE_" + role.getTag()));
        });

        // ⭐ 细粒度权限不加前缀(直接用 identifier)
        userAuthorities.forEach(auth -> {
            authorities.add(new SimpleGrantedAuthority(auth.getIdentifier()));
        });

        return new org.springframework.security.core.userdetails.User(
                userInfo.getEmail(),
                "",           // 密码为空(Vega 不验密码,靠 SSO Cookie)
                authorities);
    }
}
🎯
两个细节值得面试追问

① 角色 ROLE_ 前缀必加：Spring Security 的 hasRole('ADMIN') 内部会自动加 ROLE_ 前缀匹配 ROLE_ADMIN。如果你存权限时没加前缀，hasRole 检查永远不通过。这是经典坑点。
② 权限（Permission）不加前缀：用 hasAuthority('contract:create') 检查细粒度权限。这套分层让"角色 = 粗粒度组"、"权限 = 细粒度操作"语义清晰。

📜InitialFilter（超短）

Javaweb/filter/InitialFilter.java（完整）
@Component
public class InitialFilter implements Filter {
    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) {
        HttpServletRequest httpRequest = (HttpServletRequest) request;
        SessionContext.initRequestInfo(httpRequest);  // 一行搞定
        chain.doFilter(request, response);
    }
}

Vega 的 InitialFilter 只干一件事：把 request 信息塞进 SessionContext（URL、IP、UA 等），方便后续 Service 层拿。具体登录态由 Spring Security 处理。

Module 03 · 重点

合同回调：@SkipLogin + HMAC 签名

Vega 里最典型的"外部回调"场景——外部合同 OA 系统签完合同后 HTTP 回调 Vega。这条链路用 @SkipLogin 跳过登录 + validSign 做 HMAC 签名验证，外加 Alerter 告警。

📜ContractController 真实代码

Javaweb/controller/ContractController.java（真实）
@RestController
@RequestMapping("/api/v1/contract")
public class ContractController {

    @Resource
    private ContractServiceV2 contractServiceV2;

    @Value("${oa.callback.secret:0723123456}")  // ⭐ OA 系统共享密钥
    private String secret;

    @Resource
    private PeacockRedisTemplate peacockRedisTemplate;

    @Value("${contract.create.lock.duration:PT2M}")  // 分布式锁 2 分钟
    private Duration contractCreateLockDuration;

    @Resource
    private AlerterHelper alerterHelper;

    // ⭐⭐ 合同回调:免登录 + 签名校验 + 告警 + 测试 mock
    @PostMapping("/callback")
    @SkipLogin                        // 免登录(SkipLoginPathScanner 扫这个)
    @TstPostMock(sleepMin = 30)        // 测试环境模拟 30ms 耗时
    public Response<String> callback(@RequestBody ContractCallbackParam param) {
        try {
            ValueValidator.requireNotNull(param, "合同回调参数不能为空");
            ValueValidator.requireNotNull(param.getVendorId(), "厂商ID不能为空");
            ValueValidator.require(param.getVendorId(), "oaContract"::equals, "厂商ID不合法");

            // ⭐ 用密钥验签(param 对象级别的 validSign 方法)
            ContractCallbackParam.validSign(param, secret);

            // 调 ServiceV2 处理
            contractServiceV2.callback(param);
            return Response.success();
        } catch (BusinessException e) {
            // ⭐⭐ Peacock Alerter:失败立即告警到钉钉/企微
            Alerter.markdown(
                new MarkdownText("合同回调失败", MarkdownText.Color.RED),
                e.getMessage(),
                AlertScene.direct(new SceneID(alerterHelper.getDefaultSceneId())));

            Logs.error("合同回调失败, param: {}, error: {}",
                    JSONObject.toJSONString(param), e.getMessage(), e);

            // ⭐ 关键:参数错误原样返回,其他异常抛出让框架处理
            if (e.getCode() == ErrorCode.PARAM_ERROR.getCode()) {
                return Response.fail(e.getCode(), e.getMessage());
            }
            throw e;
        }
    }
}
🔑
这个方法值得讲 5 个点

① @SkipLogin：注解驱动免登录（外部系统哪来的 Cookie）。SkipLoginPathScanner 启动时扫描所有带此注解的方法收集路径。
② vendorId 白名单：require(vendorId, "oaContract"::equals, ...) 三参版 require，断言 vendorId 必须是 "oaContract"。Stream::Predicate 风格校验，比 if-else 优雅。
③ 签名校验：ContractCallbackParam.validSign(param, secret) 是 POJO 对象的静态方法，内部做 HMAC 验证。
④ Peacock Alerter 告警：Alerter.markdown(...) 直接发 Markdown 格式告警到钉钉/企微群。Color.RED 强调严重。
⑤ 错误分级处理：参数错误（PARAM_ERROR）返回业务失败；其他业务异常抛出让 OA 系统重试。

⏱️配置中的 Duration 风格

@Value("${contract.create.lock.duration:PT2M}")——ISO 8601 时长格式：

Duration 字符串含义
PT30S30 秒
PT2M2 分钟
PT1H1 小时
PT24H 或 P1D1 天
PT10M30S10 分 30 秒
💡
为啥用 Duration 而不是 long？

用 long timeoutMs = 120000 和用 Duration timeout = Duration.ofMillis(120000) 区别：
① 配置里写 PT2M 比 120000 可读 10 倍；
② 运维改配置时一眼知道是 2 分钟；
③ 运算安全：timeout.plus(Duration.ofSeconds(30)) 不会搞错单位；
④ 容易转换：.toMillis() / .toSeconds() / .toMinutes() 一键切换。

回调 + 签名
1. @SkipLogin 的作用？
A.没啥
B.标注该方法跳过登录校验，启动时由 SkipLoginPathScanner 扫出来加入白名单
C.跳过所有 Filter
D.允许游客访问
答案 B。运行时 LoginFilter 检查请求路径是否在 SkipLoginPathScanner.getSkipLoginPaths() 集合里，在就放行。其他 Filter 照常执行（比如 BasicFilter 的 CORS、签名校验等）。
2. @Value("${contract.create.lock.duration:PT2M}") 的 PT2M 是啥？
A.自定义字符串
B.ISO 8601 标准时长格式，= 2 分钟
C.Peacock 特殊语法
D.无意义
答案 B。ISO 8601 时长：P = Period, T = Time, M = Minutes。PT2M = 2 分钟。Spring 原生支持 Duration 类型的 @Value 自动解析。
3. 回调方法为啥要在 catch 里 throw e？
A.随意
B.参数错返回业务失败(OA 不会重试)，其他业务异常让 OA 识别为失败好重试
C.必须抛
D.Java 要求
答案 B。巧妙的错误分级：
• 参数非法 → 再重试也没用（数据本来就错） → 返回 200 + fail，OA 不重试。
• 其他业务异常 → 可能瞬时性问题 → 抛异常，框架返回 500，OA 会重试。

🔧FileTaskJob：扫描超时任务

Javajob/FileTaskJob.java（真实）
@Slf4j
@Component
public class FileTaskJob {

    @Resource
    private FileTaskManager fileTaskManager;

    @Resource
    private FileTaskConfig fileTaskConfig;

    @Value("${file-upload.task.timeout:PT10M}")  // 任务超时 10 分钟
    private Duration taskTimeout;

    @Value("${file-upload.temp-file.expire:PT24H}")  // 临时文件保留 24h
    private Duration tempFileExpire;

    // ⭐ 用 XXL-Job 不是 @Scheduled
    @XxlJob("fileUploadTaskTimeoutJob")
    public void scanAndHandleTimeoutTasks() {
        try {
            log.info("FileUploadTaskJob scanAndHandleTimeoutTasks start");

            // 3 种"未完结"状态
            List<Integer> processingStatusList = Arrays.asList(
                    FileTaskStatusEnum.QUEUED.getStatus(),
                    FileTaskStatusEnum.DOWNLOADING.getStatus(),
                    FileTaskStatusEnum.PROCESSING.getStatus()
            );
            List<FileUploadTaskDO> processingTasks = fileTaskManager.getTaskByStatus(processingStatusList);

            if (CollectionUtils.isEmpty(processingTasks)) {
                return;
            }

            int timeoutCount = 0;
            for (FileUploadTaskDO task : processingTasks) {
                if (fileTaskManager.isTimeout(task, taskTimeout.toMinutes())) {
                    handleTimeoutTask(task);
                    timeoutCount++;
                }
            }
        } catch (Exception e) {
            log.error("FileUploadTaskJob error", e);
        }
    }
}
🚨
XXL-Job vs Spring @Scheduled

Vega 用 XXL-Job 而不是 Spring 原生 @Scheduled——为啥？
① 集中调度：所有 Job 在 XXL-Job 控制台可视化管理，手动触发、失败重试、执行历史一目了然。
② 分布式协调：多实例部署时 XXL-Job 负责只让一个实例跑，不需要自己写分布式锁。
③ 动态调度：改执行时间不用改代码/重启（@Scheduled 必须重启）。
④ 依赖编排：支持 Job 依赖链（A 跑完再跑 B）。
这是大厂 B 端常见架构。Nova 是 C 端用 @Scheduled 就够，Vega 是 B 端批处理多必须上 XXL-Job。

🧪 检验理解 · Module 4
文件任务
1. 为啥 FileTaskJob 扫 3 个状态（QUEUED/DOWNLOADING/PROCESSING）？
A.代码冗余
B.这 3 个都是"未完结"中间态，任务可能卡在任一阶段
C.数据库规范
D.性能
答案 B。任务生命周期：QUEUED（刚创建）→ DOWNLOADING（从 COS 拉）→ PROCESSING（解析入库）→ SUCCESS/FAILED。任一中间态如果实例崩溃都可能卡住。Job 把 3 个中间态都扫，超过 10 分钟还没完结的标记为 TIMEOUT 并发告警。
2. Vega 为啥选 XXL-Job 而不是 Spring @Scheduled？
A.性能
B.集中调度 + 分布式协调 + 动态调度 + 依赖编排
C.团队偏好
D.历史遗留
答案 B。B 端 11 个 Job 需要集中管理、多实例协调、动态改时间——@Scheduled 这些都不支持。XXL-Job 有可视化控制台，这在运维侧是巨大加分项。

🔧ContractMonitorJob 真实代码

Javajob/ContractMonitorJob.java（片段）
@Component
public class ContractMonitorJob {

    @Resource
    private UploaderWorksDriver uploaderWorksDriver;   // TRPC 驱动

    @Resource
    private OrgCoopApplyDriver orgCoopApplyDriver;      // TRPC 驱动

    @Resource(name = "cacheRedisTemplate")
    private PeacockRedisTemplate cacheRedisTemplate;

    // ⭐ 配置由 Peacock 热更新
    @Resource
    private ContractMonitorTemplate contractMonitorTemplate;

    @XxlJob("contractMonitorJob")
    public void monitor() {
        // ⭐ 从 XxlJobHelper 拿调度参数
        String param = XxlJobHelper.getJobParam();
        try {
            // 1. 查最近一批合同
            WorksListQuery query = new WorksListQuery();
            query.setStatusList(Arrays.asList(ContractStatus.SIGNING));
            PagedData<UploaderWorksDO> pagedData = uploaderWorksDriver.listByQuery(query);

            // 2. 过滤"超过 N 天未签"的
            List<UploaderWorksDO> timeoutWorks = new ArrayList<>();
            for (UploaderWorksDO work : pagedData.getData()) {
                if (isOverDue(work.getCreateTime(), 7)) {
                    timeoutWorks.add(work);
                }
            }

            // 3. 用 StringSubstitutor 格式化告警内容
            Map<String, String> vars = new HashMap<>();
            vars.put("count", String.valueOf(timeoutWorks.size()));
            String msg = StringSubstitutor.replace(contractMonitorTemplate.getTemplate(), vars);

            // 4. 发 Peacock Alerter 告警
            Alerter.markdown(
                new MarkdownText("合同超时监控", MarkdownText.Color.WARNING),
                msg, AlertScene.direct(new SceneID("contract-alert")));
        } catch (Exception e) {
            Logs.error("ContractMonitorJob error", e);
            XxlJobHelper.handleFail(ExceptionAid.getStackTrace(e));
        }
    }
}
💡
XxlJobHelper.getJobParam() 的妙用

XXL-Job 控制台可以给 Job 传参数，代码里用 XxlJobHelper.getJobParam() 拿到。用途：
① 灰度启动：参数传 dryRun=true，只扫不告警，验证逻辑正确性。
② 指定范围：参数传 orgId=123，只处理特定机构的数据。
③ 手动触发：运营平台触发时传 force=true 跳过 Redis 缓存强制从 DB 拉。
这种"参数化任务"比 @Scheduled 灵活很多。

答案 B。XXL-Job 控制台可以给任务传字符串参数。代码 XxlJobHelper.getJobParam() 拿到后 parse 用来控制行为。让 Job 支持"参数化运行"，这是比 @Scheduled 强大的地方。

🎯AlertScene 的设计

AlertScene 决定告警发到哪个群、发给谁、按什么策略聚合。这是运维侧治理告警的关键抽象。

💡
告警治理原则

① 分场景：合同相关告警发"合同群"，结算告警发"财务群"——SceneID 区分。
② 分级别：RED/WARNING/INFO 三色对应不同群或不同 @ 范围。
③ 聚合防骚扰：同一告警 1 分钟内只发 1 次（通过 SceneID 聚合）。
④ 告警即日志：所有告警自动写入日志，可追溯。
这是大厂级告警体系的最佳实践，远好于"全部 @all"式的告警。

1. Vega 和 Nova 最大的差异是什么？
A.编程语言
B.面向 B 端 vs C 端：Vega 有大量 XXL-Job 批处理、Spring Security 权限、告警体系
C.技术栈
D.没区别
答案 B。Nova 是 C 端面向 UP 主（简单权限、少批处理），Vega 是 B 端面向运营（复杂权限、多批处理、需告警）。"B 端多 Job"、"C 端多 API"是通用规律。
