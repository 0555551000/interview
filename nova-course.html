Module 01

这个应用是做什么的

包名 com.yuewen.openplatform.nova，是阅文漫剧面向 UP 主（C 端）的后端服务。承接注册、身份核验、素材签约、资产查看一站式操作。

🎬一个 UP 主"小雨"的故事

小雨是一位漫剧 AI 真人赛道的创作者。她要：

  1. 注册账号（用阅文账号 ywguid + ywkey Cookie 登录）
  2. 填资料（POST /api/v1/me/add 或 /addwithworks）
  3. 身份核验（POST /api/v1/me/idverify，内部调实名 + 活体）
  4. 签约合同 → 查资产 → 等收益
💡
三兄弟关系

Nova（C 端，UP 主）、Vega（B 端，运营）、Comic Drama Web（B 端，分销商）。三者共享底层 Peacock Driver Uploader 数据访问层（TRPC），但用户群完全不同。

Module 02

Filter 链真相

Nova 只有 3 个 Filter：BasicFilter（CORS + Wrapper 切换）、LoginFilter（Cookie 校验 + debug 模式）、APFilter（日志）。本节重点看前两个。

📜BasicFilter 真实代码

Javaweb/filter/BasicFilter.java
@Component
public class BasicFilter implements Filter {

    @Value("${access.control.allow.origin}")
    String accessAllowOrigin;

    @Value("${header.encrypt.open:true}")
    private boolean encryptOpen;

    @Resource
    private RequestInitSpec requestInit;

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) {
        HttpServletResponse response = (HttpServletResponse) res;
        HttpServletRequest request = (HttpServletRequest) req;

        // ① multipart 请求直接放行(不包装,避免破坏文件上传)
        if (isMultipartRequest(request)) {
            chain.doFilter(request, res);
            return;
        }

        // ② ⭐ 根据环境选择 Wrapper
        HttpServletRequest wrapperRequest;
        if (Context.getEnv() != Env.PRODUCT && !encryptOpen) {
            // 非生产 + 不加密:PostRequestWrapper (仅可重读 body)
            wrapperRequest = new PostRequestWrapper(request);
        } else {
            // 生产或加密:XssAndSqlHttpServletRequestWrapper (可重读 + XSS/SQL 过滤)
            wrapperRequest = new XssAndSqlHttpServletRequestWrapper(request);
        }

        // ③ Peacock 框架初始化 TypicalResolved 请求上下文
        initReq(request);

        // ④ ⭐ CORS 动态 Origin 匹配(不是写死的)
        String allowOrigin = null;
        if (StringUtils.isNotBlank(accessAllowOrigin)) {
            String[] split = accessAllowOrigin.split(",");
            String origin = request.getHeader("Origin");
            allowOrigin = split[0]; // 默认第一个
            for (String s : split) {
                if (StringUtils.isNotEmpty(origin) && origin.contains(s)) {
                    // ⭐ 匹配后缀(防止 evilyuewen.com 伪造)
                    String hostSuffix = origin.substring(origin.length() - s.length());
                    if (s.equals(hostSuffix)) {
                        allowOrigin = origin;
                        break;
                    }
                }
            }
        }

        response.setHeader("Access-Control-Allow-Credentials", "true");
        if (allowOrigin != null) {
            response.setHeader("Access-Control-Allow-Origin", allowOrigin);
        }
        response.setHeader("Access-Control-Max-Age", "86400");
        // ... 其他 CORS headers

        if ("OPTIONS".equalsIgnoreCase(request.getMethod())) {
            response.setStatus(HttpServletResponse.SC_OK);
        } else {
            chain.doFilter(wrapperRequest, res);
        }
    }
}
🔑
3 个值得注意的细节

① 环境 + 开关双条件切换 Wrapper：生产环境强制 XSS/SQL 过滤，开发环境可以关掉方便调试。
② CORS 动态匹配 + 后缀校验：防伪造。配置 yuewen.com,readnovel.com，恶意的 evilyuewen.com 因为后缀不一致被拒。
③ multipart 请求直接放行：不包装，避免 MultipartFile 解析被破坏。

🔐LoginFilter 真实代码（含 debug 模式）

Javaweb/filter/LoginFilter.java（关键片段）
@Slf4j
@Component
public class LoginFilter implements Filter {

    @Resource private SkipLoginPathScanner skipLoginPathScanner;
    @Resource private UserManager userManager;
    @Resource private ProfileManager profileManager;

    @SneakyThrows
    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) {
        HttpServletRequest httpRequest = (HttpServletRequest) request;
        HttpServletResponse httpResponse = (HttpServletResponse) response;
        String path = httpRequest.getRequestURI();

        // ① 白名单放行(启动时 SkipLoginPathScanner 扫出来的)
        if (skipLoginPathScanner.getSkipLoginPaths().contains(path)) {
            chain.doFilter(request, response);
            return;
        }

        try {
            // ② ⭐ 非生产环境的 debug 模式(带 debug header + guid header 可伪装登录)
            if (allowDebug(httpRequest)) {
                useDebugMode(httpRequest, httpResponse);
                chain.doFilter(request, response);
                return;
            }

            // ③ 检查 ywguid + ywkey Cookie 都在
            boolean hasCookie = SessionContext.checkUserCookie(httpRequest);
            if (!hasCookie) {
                setInvalidSessionResponse(httpResponse);
                return;
            }

            // ④ 从 Cookie 取 guid 和 key
            long ywGuidFromCookie = SessionContext.getYwGuidFromCookie(httpRequest);
            String ywKeyFromCookie = SessionContext.getYwKeyFromCookie(httpRequest);

            // ⑤ 调 UserManager 去阅文账号中心验证
            boolean userAuth = userManager.userAuth(ywKeyFromCookie, ywGuidFromCookie, httpRequest.getRemoteAddr());
            if (!userAuth) {
                setInvalidSessionResponse(httpResponse);
                return;
            }

            // ⑥ 查 UP 主档案
            Result<UploaderProfile> userInfoResult = profileManager.query(ywGuidFromCookie);
            if (userInfoResult.isFailure()) {
                setInvalidSessionResponse(httpResponse);
                return;
            }

            // ⑦ ⭐ 设置线程上下文 + MDC traceId
            SessionContext.setUserLocal(ywGuidFromCookie, userInfoResult.dataRequireNonNull());
            MDC.put("guid", String.valueOf(ywGuidFromCookie));

            chain.doFilter(request, response);
        } catch (Exception e) {
            setInvalidSessionResponse(httpResponse);
        } finally {
            // ⑧ ⭐⭐ 必须清 ThreadLocal,防线程池复用导致上下文串
            SessionContext.clear();
        }
    }

    private boolean allowDebug(HttpServletRequest httpRequest) {
        String debugHeader = httpRequest.getHeader("debug");
        return Env.current() != Env.PRODUCT && StringUtils.isNotEmpty(debugHeader);
    }
}
⚠️
两个细节值得面试追问

① Debug 模式：非生产环境 + debug header 存在 + guid header 提供用户 ID，可跳过 Cookie 验证直接"登录"。开发/联调神器。但生产环境强制关闭（Env.current() != PRODUCT 判断）。
② finally 里 SessionContext.clear()：ThreadLocal 必须清，否则线程池复用时下一个请求的用户会拿到上一个请求的上下文——严重的信息泄露漏洞。

🧩SkipLoginPathScanner 真实代码

和 Comic Drama Web 几乎一模一样（阅文通用组件）——启动时扫描 @Controller 的方法，收集 @SkipLogin 注解的路径：

Javaweb/SkipLoginPathScanner.java
@PostConstruct
public void scanSkipLoginPaths() {
    String[] controllerBeanNames = applicationContext.getBeanNamesForAnnotation(Controller.class);
    for (String beanName : controllerBeanNames) {
        processControllerBean(beanName);
    }
}

private void processControllerBean(String beanName) {
    Object bean = applicationContext.getBean(beanName);
    // ⭐ 穿透 Spring AOP 代理拿真实类
    Class<?> beanClass = AopUtils.getTargetClass(bean);
    String baseUrl = getBaseUrl(beanClass);

    Arrays.stream(beanClass.getMethods())
            .filter(m -> m.isAnnotationPresent(SkipLogin.class))
            .forEach(method -> {
                String methodUrl = extractMethodUrl(method);
                if (methodUrl != null) {
                    skipLoginPaths.add(normalizeUrl(baseUrl, methodUrl));
                }
            });
}
🧪 检验理解 · Module 2
Filter 链
1. BasicFilter 在什么情况下用 PostRequestWrapper 而不是 XssAndSqlHttpServletRequestWrapper？
A.永远用 Xss
B.非生产环境 + header.encrypt.open=false 时用 PostRequestWrapper（方便调试 body）
C.multipart 请求
D.随机
答案 B。代码逻辑：if (Context.getEnv() != Env.PRODUCT && !encryptOpen)。开发环境方便查看原始 body 用轻量 Wrapper，生产强制 XSS 过滤。
2. CORS Origin 为什么要做"后缀匹配"？
A.好玩
B.防 evilyuewen.com 这种伪造域名通过 contains 校验
C.性能
D.标准
答案 B。如果只用 origin.contains("yuewen.com")，https://evilyuewen.com.hack.com 也能通过。加 hostSuffix.equals(s) 做后缀匹配确保域名是"以 yuewen.com 结尾"，而不是"包含 yuewen.com"。
3. LoginFilter 的 finally { SessionContext.clear(); } 为什么关键？
A.好习惯
B.防止线程池复用时，下一请求拿到上一请求的用户上下文（信息泄露漏洞）
C.性能
D.Java 语法
答案 B。ThreadLocal 绑定线程，Servlet 容器的线程池会复用线程。如果处理完请求不 clear，下一个请求复用同一线程时可能读到"上一个用户的 user 对象"——严重的安全问题。这是 ThreadLocal 的经典陷阱。
4. debug 模式的价值？
A.后门
B.非生产环境下开发 / 联调时可以模拟任意用户，无需真实登录（生产强制关闭）
C.性能测试
D.无用
答案 B。前端联调/测试/开发时，不想每次都走完整 Cookie 登录流程，加 debug: 1 + guid: 123456 两个 header 就能"模拟登录"。生产环境 Env.current() != PRODUCT 判断强制关闭这个入口。
Module 03 · 重点

SessionContext 深度解读

Nova 里最重要的基础类，14k 字符。基于 TransmittableThreadLocal，处理用户上下文的存/取/传/清。本节逐函数讲。

🧵完整类结构

Javahelper/SessionContext.java（真实）
@Slf4j
public final class SessionContext {
    private User user;

    // ⭐ 关键:用 TransmittableThreadLocal,不是 ThreadLocal
    private static final ThreadLocal<SessionContext> SESSION_THREAD_LOCAL
            = new TransmittableThreadLocal<>();

    // Cookie 名:走阅文 SSO 通用
    public static final String YW_GUID_COOKIE_NAME = "ywguid";
    public static final String YW_KEY_COOKIE_NAME  = "ywkey";

    // 离线上下文:Job/定时/自动化场景不走登录,构造一个虚拟 user
    public static SessionContext createOfflineContext() {
        SessionContext ctx = new SessionContext();
        ctx.user = User.builder().guid(-1L).phone("").build();
        SESSION_THREAD_LOCAL.set(ctx);
        return ctx;
    }

    // Cookie 检查:两个必须都在
    public static boolean checkUserCookie(HttpServletRequest request) {
        if (request == null || request.getCookies() == null) return false;
        boolean hasGuid = Arrays.stream(request.getCookies())
                .filter(Objects::nonNull)
                .anyMatch(c -> YW_GUID_COOKIE_NAME.equals(c.getName()));
        boolean hasKey = Arrays.stream(request.getCookies())
                .filter(Objects::nonNull)
                .anyMatch(c -> YW_KEY_COOKIE_NAME.equals(c.getName()));
        return hasGuid && hasKey;
    }

    // 设 user(LoginFilter 验证通过后调用)
    public static void setUserLocal(long guid, UploaderProfile userInfo) {
        if (guid <= 0 || userInfo == null) return;
        getOrCreateContext().user = User.builder()
                .guid(guid)
                .phone(userInfo.getPhoneNumber())
                .longinTime(LocalDateTime.now())
                .nickName(userInfo.getNickName())
                .douyinAccount(userInfo.getDouyinAccount())
                .wechatContact(userInfo.getWechatContact())
                .email(userInfo.getEmail())
                .verified(userInfo.isVerified())
                .orgId(userInfo.getOrgId())
                .orgName(userInfo.getOrgName())
                .userType(userInfo.getUserType())
                .collaboratorType(userInfo.getCollaboratorType())
                .build();
    }

    // 取 user(业务代码高频调用)
    public static User getUserRequired() {
        User user = getUser();
        if (user == null) {
            throw new BusinessException(ErrorCode.USER_NOT_FOUND);
        }
        return user;
    }

    // ⭐⭐ 清理:每次请求结束都要调
    public static void clear() {
        SESSION_THREAD_LOCAL.remove();
    }
}

💡为什么是 TransmittableThreadLocal

对比ThreadLocalInheritableThreadLocalTransmittableThreadLocal
父线程→子线程（new Thread）❌✅✅
线程池复用（Executor）❌❌✅（需 TtlExecutors.getTtlExecutor 包装）
异步任务 CompletableFuture.supplyAsync❌❌✅
跨 RPC 调用❌❌需额外适配
🎯
Nova 为啥必用 TTL 而不是普通 ThreadLocal

看 MeController.add 方法：
Context.current().wrap(asyncPool).execute(() -> userManager.updateUserTagForAnimation(SessionContext.getUserRequired().getGuid(), ...))

异步线程里必须能拿到主线程的 User。如果用普通 ThreadLocal，getUserRequired() 会返回 null 抛异常。InheritableThreadLocal 解决 new Thread() 但解决不了线程池（线程池的线程一开始 new 出来时没上下文）。

TTL 的原理：提交任务时快照当前线程 ThreadLocal 值，执行前 set 到目标线程，执行完 remove。需要配合 TtlExecutors.getTtlExecutor(originalExecutor) 包装。

Javaweb/controller/MeController.java
@RestController
@RequestMapping("/api/v1/me")
public class MeController {

    @Resource private ProfileService profileService;
    @Resource private UserManager userManager;
    @Resource(name = "asyncPool")
    private Executor asyncPool;

    // 查资料
    @GetMapping("/show")
    public Response<UserDetailVO> show() {
        return Response.success(profileService.getUserDetail());
    }

    // 批量添加(资料 + 作品)
    @PostMapping("/addwithworks")
    @TstPostMock  // 测试环境自动 mock
    public Response<Void> addWithWorks(@RequestBody ProfileWithWorksAddParam param) {
        param.forceMarkPiracy();
        profileService.addProfileWithWorksForUp(param, ProfileWithWorksAddParam::checkRequiredWork);
        return Response.success();
    }

    // 添加(可选作品)+ ⭐ 异步打标签
    @PostMapping("/add")
    @TstPostMock
    public Response<Void> add(@RequestBody ProfileWithWorksAddParam param) {
        profileService.addProfileWithWorksForUp(param, p -> {
            if (CollectionUtils.isEmpty(p.getWorks())) {
                p.checkProfile();
            } else {
                p.checkRequiredWork();
            }
        });

        // ⭐⭐ 异步执行 + 保留上下文(TTL 传递)
        Context.current().wrap(asyncPool).execute(() -> {
            userManager.updateUserTagForAnimation(
                SessionContext.getUserRequired().getGuid(),  // 需要 TTL
                param.getCollaboratorType());
        });
        return Response.success();
    }

    // 实名认证
    @PostMapping("/idverify")
    @TstPostMock(sleepMin = 80, sleepMax = 200)  // 测试环境模拟 80-200ms 耗时
    public Response<Void> idVerify(@RequestBody IdVerifyParam param) {
        ValueValidator.requireNotEmpty(param.getName(), "name required");
        ValueValidator.requireNotEmpty(param.getIdCard(), "idCard required");
        profileService.idVerify(param);
        return Response.success();
    }
}
✨
3 个细节值得聊

① @TstPostMock 注解：Peacock 内部的测试增强，测试环境自动返回 mock 数据。可加 sleepMin/sleepMax 模拟网络延迟。
② Context.current().wrap(asyncPool)：不是直接 asyncPool.execute()，而是先 wrap 再 execute——目的是把当前的 io.opentelemetry.Context（含 TraceId）也传到异步线程，这样异步任务的日志能串联起主链路的 trace。
③ 方法级参数校验：ValueValidator.requireNotEmpty(..., "name required") 抛 IllegalArgumentException，被 GlobalExceptionHandler 翻译成 PARAM_ERROR。

🧪 检验理解 · Module 3
SessionContext 与上下文
1. User 对象里有多少个字段？
A.3-4 个
B.12 个（guid/phone/longinTime/nickName/douyinAccount/wechatContact/email/verified/orgId/orgName/userType/collaboratorType）
C.只有 guid
D.20+ 个
答案 B。从 setUserLocal 的 Builder 可以数出 12 个字段。业务代码里 SessionContext.getUserRequired().getOrgId() 可以直接拿到当前 UP 主的组织 ID——因为登录时就一起拉下来了。
2. Context.current().wrap(asyncPool).execute(...) 和 asyncPool.execute(...) 区别？
A.一样
B.wrap 版本会把当前 OpenTelemetry Context（含 TraceId）传到异步线程，日志可串联
C.性能更好
D.随机
答案 B。io.opentelemetry.context.Context 负责分布式 trace。异步执行前用 wrap 包一下 Executor，确保异步任务执行时自动恢复上下文。加上 TTL，User 上下文 + Trace 上下文都能传过去。
3. 线程池里如果不用 TTL，会发生什么？
A.什么都不会
B.异步任务 SessionContext.getUserRequired() 抛 USER_NOT_FOUND 异常；或更糟，拿到前一个用户的 User（如果线程复用时没清）
C.性能变差
D.什么都正常
答案 B。普通 ThreadLocal 不传递，异步任务里 getUser() 返回 null。如果刚好线程池复用了一个没 clear 的线程，更可怕——会拿到别人的 User，发生严重的数据隔离错误。所以 Nova 配合 asyncPool 和 TTL 使用。

🔒AESStringTypeHandler：MyBatis 透明加解密

Javautil/AESStringTypeHandler.java（完整真实）
public class AESStringTypeHandler extends BaseTypeHandler<String> {

    @Override
    public void setNonNullParameter(PreparedStatement ps, int i,
                                    String parameter, JdbcType jdbcType) throws SQLException {
        // ⭐ 写入 DB 前加密
        ps.setString(i, CommonAES.encryptWithBase64(parameter));
    }

    @Override
    public String getNullableResult(ResultSet rs, String columnName) throws SQLException {
        // ⭐ 从 DB 读时解密
        return CommonAES.decryptWithBase64(rs.getString(columnName));
    }

    @Override
    public String getNullableResult(ResultSet rs, int columnIndex) throws SQLException {
        return CommonAES.decryptWithBase64(rs.getString(columnIndex));
    }

    @Override
    public String getNullableResult(CallableStatement cs, int columnIndex) throws SQLException {
        return CommonAES.decryptWithBase64(cs.getString(columnIndex));
    }
}
✨
TypeHandler 的 3 个方法为啥都要重写

BaseTypeHandler<String> 是 MyBatis 的 TypeHandler 基类，必须实现：
① setNonNullParameter：写 DB 时（PreparedStatement.setString）
② getNullableResult(ResultSet, String)：按列名读（SELECT phone FROM ...）
③ getNullableResult(ResultSet, int)：按列索引读（SELECT * FROM ...）
④ getNullableResult(CallableStatement, int)：存储过程返回值
少写任何一个，相应场景就会拿到密文。Nova 这个 TypeHandler 写齐了所有情况。业务代码零感知，Mapper XML 的 resultMap 声明 typeHandler="AESStringTypeHandler" 即可。

缓存与安全

Nova 有一个小而精的 RedisCacheHelper（不到 50 行），专门做批量清缓存。配合 AESStringTypeHandler，这两个就是 Nova 的"缓存 + 安全"双基建。

🔨RedisCacheHelper：SCAN 批量删

Javahelper/RedisCacheHelper.java（完整真实）
@Slf4j
public final class RedisCacheHelper {
    public PeacockRedisTemplate redisTemplate;

    // ⭐ 静态工厂 + 私有构造,保证 redisTemplate 必注入
    private RedisCacheHelper() {}

    public static RedisCacheHelper getInstance(PeacockRedisTemplate cacheRedisTemplate) {
        RedisCacheHelper instance = new RedisCacheHelper();
        instance.redisTemplate = cacheRedisTemplate;
        return instance;
    }

    public int deleteAllCacheByPattern(String pattern) {
        if (null == redisTemplate) {
            throw new IllegalStateException("RedisTemplate is not initialized");
        }
        final Set<String> keysToDelete = new HashSet<>();

        redisTemplate.executeVoid(connection -> {
            // ⭐ 用 SCAN 而不是 KEYS,避免阻塞 Redis
            ScanOptions options = ScanOptions.scanOptions()
                .match(pattern)
                .count(100)  // 每批扫 100 个
                .build();

            try (Cursor<String> cursor = connection.scan(options)) {
                while (cursor.hasNext()) {
                    keysToDelete.add(new String(cursor.next().getBytes(), StandardCharsets.UTF_8));
                }
            }
        });

        if (!keysToDelete.isEmpty()) {
            redisTemplate.executeVoid(tpl -> tpl.delete(keysToDelete));
            log.info("已删除匹配[{}]的缓存，共{}个", pattern, keysToDelete.size());
        } else {
            log.info("未找到匹配[{}]的缓存", pattern);
        }
        return keysToDelete.size();
    }
}
🚨
KEYS vs SCAN — 血淋淋的教训

KEYS 是 O(N) + 阻塞整个 Redis。Redis 单线程，KEYS 执行期间所有其他请求排队。如果 Redis 里有几百万 key，一次 KEYS 可能让 Redis 卡 3-5 秒——生产环境直接告警。

SCAN 是游标增量遍历，每次只扫一小批（count(100)），不阻塞其他请求。缺点是可能重复扫或漏扫（游标重试场景），但用于"清缓存"完全可接受。

面试追问："SCAN 会不会漏 key？" 答："SCAN 期间新写入的 key 可能扫不到，但这对'清理已有缓存'场景不影响。如果要求严格准确，可以 SCAN + 间隔再 SCAN 一次兜底。"

全局异常处理

只有 1 个类、4 个 handler，但哲学值得讲。

🛡️真实 GlobalExceptionHandler

Javaweb/GlobalExceptionHandler.java（完整真实）
@Slf4j
@ControllerAdvice
public class GlobalExceptionHandler {

    // 1. 兜底:所有未捕获异常
    @ExceptionHandler(Exception.class)
    @ResponseBody
    public String handleException(Exception e) {
        // ⭐ 注意:这里是 log.info 不是 error
        log.info("found exception, msg={}", e.getMessage(), e);
        return JSONObject.toJSONString(Response.fail(ErrorCode.INNER_EXCEPTION));
    }

    // 2. 参数非法(业务主动抛 IllegalArgumentException)
    @ExceptionHandler(IllegalArgumentException.class)
    @ResponseBody
    public String handleIllegalArgumentException(Exception e) {
        log.error("found IllegalArgument exception, msg={}", e.getMessage(), e);
        return JSONObject.toJSONString(
            Response.fail(ErrorCode.PARAM_ERROR.getCode(), e.getMessage()));
    }

    // 3. Spring 的参数缺失异常(比如 @RequestParam 没传)
    @ExceptionHandler(MissingRequestValueException.class)
    @ResponseBody
    public String handleMissingRequestValueException(MissingRequestValueException e) {
        log.info("found MissingRequestValueException, msg={}", e.getMessage());
        return JSONObject.toJSONString(
            Response.fail(ErrorCode.PARAM_ERROR.getCode(), e.getMessage()));
    }

    // 4. 业务异常:带自定义错误码
    @ExceptionHandler(BusinessException.class)
    @ResponseBody
    public String handleBusinessExceptionException(BusinessException e) {
        log.info("found BusinessException, msg={}", e.getMessage());
        return JSONObject.toJSONString(Response.fail(e.getCode(), e.getMessage()));
    }
}

🎓日志级别的哲学

异常类型日志级别原因
BusinessExceptionlog.info业务正常分支（用户没权限/数据不存在），日志量大，不需要告警
MissingRequestValueExceptionlog.info前端没传参，多半是客户端 bug，不是我们的问题
IllegalArgumentExceptionlog.error服务端自己抛的参数非法，应该告警
Exception（兜底）log.info包含 stack trace，但意外是小概率事件
💡
为啥 BusinessException 不打 error

一个常见误区：把所有异常都打 error。但业务异常是"预期内"的东西——用户未登录、数据不存在、订单状态不对——每天发生几十万次。如果打 error，告警平台会被淹没；真正的系统故障（DB 断连）反而看不见。

分级原则：
• error：需要立即人工介入的事
• info：记录但不告警
• debug：仅开发查看
