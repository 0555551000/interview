📜BasicFilter 真实代码

Javaweb/filter/BasicFilter.java
@Component
@WebFilter(filterName = "basicFilter")
public class BasicFilter implements Filter {

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) {
        HttpServletResponse response = (HttpServletResponse) res;
        HttpServletRequest request = (HttpServletRequest) req;

        // ① 包装让 body 可重读
        HttpServletRequest wrapperRequest = new PostRequestWrapper(request);

        // ② 设置 CORS 响应头
        response.setHeader("Access-Control-Allow-Credentials", "true");
        response.setHeader("Access-Control-Max-Age", "86400");
        response.setHeader("Access-Control-Allow-Methods", "*");
        response.setHeader("Access-Control-Allow-Headers",
            "x-requested-with, authorization, Content-Type, credential, ywHeader, sign, platform");

        // ③ OPTIONS 预检直接 200
        if ("OPTIONS".equalsIgnoreCase(request.getMethod())) {
            response.setStatus(HttpServletResponse.SC_OK);
        } else {
            chain.doFilter(wrapperRequest, res);
        }
    }
}
🔑
3 个细节

① Max-Age=86400：预检缓存 24 小时。
② 允许 ywHeader, sign, platform：阅文自定义业务 Header。
③ OPTIONS 直接 200：预检不走业务。

Module 03 · 重点

HMAC 内部鉴权 100% 真实代码

本教程最有价值的一块。分销商的程序化调用走 InternalAuthFilter 做 HMAC-SHA256 签名。配套 InternalSignUtil（签名）、InternalAuthConfig（配置）、CachedBodyRequestWrapper（body 重读）。面试能讲 15 分钟。

🎯签名设计的 4 个决策

决策点做法为什么
签名算法HMAC-SHA256带密钥的 Hash，比纯 MD5 安全
签名内容5 段换行：method + path + query + body MD5 + ts + noncebody 参与防篡改，MD5 先压省 CPU
防重放Timestamp + Noncets 限时效，nonce 防窗口内重放
比对constantTimeEquals XOR 定时防时序侧信道攻击

🔐第 1 步：InternalSignUtil

Javautil/InternalSignUtil.java（真实）
public class InternalSignUtil {

    public static final String HEADER_TIMESTAMP = "X-Internal-Timestamp";
    public static final String HEADER_NONCE     = "X-Internal-Nonce";
    public static final String HEADER_SIGN      = "X-Internal-Sign";
    private static final String HMAC_ALGO = "HmacSHA256";

    // 核心签名方法
    public static String sign(String secret, String method, String path,
                              Map<String, String> queryParams, String body,
                              String timestamp, String nonce) {
        String canonicalQuery = canonicalQuery(queryParams);

        // ⭐ body 先 MD5 —— 省 CPU + 防篡改
        String bodyMd5 = StringUtils.isEmpty(body) ? "" : DigestUtils.md5Hex(body);

        // ⭐ 5 段换行拼接（AWS SigV4 / 阿里云都这样）
        String payload = String.join("\n",
                method.toUpperCase(), path, canonicalQuery, bodyMd5, timestamp, nonce);
        return hmacSha256Hex(secret, payload);
    }

    // TreeMap 字典序 + URL 编码（+ → %20）
    public static String canonicalQuery(Map<String, String> params) {
        if (params == null || params.isEmpty()) return "";
        TreeMap<String, String> sorted = new TreeMap<>(params);
        return sorted.entrySet().stream()
                .map(e -> e.getKey() + "=" + urlEncode(StringUtils.defaultString(e.getValue())))
                .collect(Collectors.joining("&"));
    }

    private static String urlEncode(String s) {
        try {
            // ⭐ URLEncoder 把空格编成 + ，RFC 3986 要 %20
            return URLEncoder.encode(s, StandardCharsets.UTF_8.name()).replace("+", "%20");
        } catch (Exception e) { return s; }
    }

    // 格式非法返回 MAX_VALUE = 超出窗口
    public static long timestampDiffMillis(String clientTimestamp) {
        try {
            long ts = Long.parseLong(clientTimestamp);
            return Math.abs(System.currentTimeMillis() - ts);
        } catch (NumberFormatException e) {
            return Long.MAX_VALUE;
        }
    }
}
🎓
3 个面试官会追问的亮点

① body 先 MD5：几 MB body 直接 HMAC 慢，MD5 压 32 字节再 HMAC，CPU 低 100 倍。AWS SigV4 / 阿里云 OSS 通用做法。
② URL 编码 + 改 %20：Java URLEncoder 空格→+，RFC 3986 要 %20。Python/Go 默认 %20，不统一签名永远对不上。这一行是踩坑证明。
③ 异常返回 MAX_VALUE：乱码时间戳直接判超时，防攻击者用乱码探测。

🛡️第 2 步：InternalAuthFilter

Javaweb/filter/InternalAuthFilter.java（真实）
@Component
public class InternalAuthFilter implements Filter {

    // 4 种明确错误码
    public static final int CODE_CONFIG_MISSING  = -40001;
    public static final int CODE_HEADER_MISSING  = -40102;
    public static final int CODE_TIMESTAMP_SKEW  = -40103;
    public static final int CODE_SIGN_INVALID    = -40101;

    @Resource
    private InternalAuthConfig internalAuthConfig;

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest req = (HttpServletRequest) request;
        HttpServletResponse resp = (HttpServletResponse) response;

        // ① 校验服务端配置
        String secret = internalAuthConfig.getInternalAuthSecret();
        if (StringUtils.isBlank(secret)) {
            writeFail(resp, CODE_CONFIG_MISSING, "internal secret not configured");
            return;
        }

        // ② 取 3 个签名 Header
        String clientTs    = req.getHeader(InternalSignUtil.HEADER_TIMESTAMP);
        String clientNonce = req.getHeader(InternalSignUtil.HEADER_NONCE);
        String clientSign  = req.getHeader(InternalSignUtil.HEADER_SIGN);
        if (StringUtils.isAnyBlank(clientTs, clientNonce, clientSign)) {
            writeFail(resp, CODE_HEADER_MISSING, "internal sign headers missing");
            return;
        }

        // ③ 时间戳偏移校验（窗口从配置读，可热更）
        long skew = InternalSignUtil.timestampDiffMillis(clientTs);
        if (skew > internalAuthConfig.getTimestampSkewMillis()) {
            writeFail(resp, CODE_TIMESTAMP_SKEW, "internal timestamp skew too large");
            return;
        }

        // ④ 包装 request 让 body 可重读
        CachedBodyRequestWrapper wrapped = new CachedBodyRequestWrapper(req);
        String body = wrapped.getBodyString();

        // ⑤ 服务端用同样算法算一遍
        String expected = InternalSignUtil.signFromRequest(secret, wrapped, body);

        // ⑥ ⭐⭐⭐ 恒定时间比对
        if (!constantTimeEquals(expected, clientSign)) {
            Logs.access.warn(">>> sign mismatch, path={}, remoteAddr={}",
                    req.getRequestURI(), req.getRemoteAddr());
            writeFail(resp, CODE_SIGN_INVALID, "internal sign invalid");
            return;
        }

        // ⑦ 传递包装过的 request，Controller 能再读 body
        chain.doFilter(wrapped, response);
    }

    // ⭐ 恒定时间比对 — 面试必考
    private static boolean constantTimeEquals(String a, String b) {
        if (a == null || b == null || a.length() != b.length()) return false;
        int diff = 0;
        for (int i = 0; i < a.length(); i++) {
            // XOR：不等就 |= 1，不提前 break
            diff |= a.charAt(i) ^ b.charAt(i);
        }
        return diff == 0;
    }
}

📦第 3 步：CachedBodyRequestWrapper 私有内部类

JavaInternalAuthFilter.CachedBodyRequestWrapper
private static class CachedBodyRequestWrapper extends HttpServletRequestWrapper {

    private final byte[] body;

    CachedBodyRequestWrapper(HttpServletRequest request) throws IOException {
        super(request);
        // ⭐ 构造时一次读 body 到 byte[]
        this.body = StreamUtils.copyToByteArray(request.getInputStream());
    }

    String getBodyString() {
        return new String(body, StandardCharsets.UTF_8);
    }

    @Override
    public ServletInputStream getInputStream() {
        ByteArrayInputStream bais = new ByteArrayInputStream(body);
        return new ServletInputStream() {
            @Override public int read() { return bais.read(); }
            @Override public boolean isFinished() { return bais.available() == 0; }
            @Override public boolean isReady() { return true; }
            @Override public void setReadListener(ReadListener listener) {}
        };
    }
}
🔑
为啥用私有内部类？

项目里有 PostRequestWrapper（BasicFilter 用的），但 Internal 鉴权链路独立、body 一次读 OK、还要保证 Controller 能再读——Filter 内部封一个私有类最简单：body 一次读到 byte[]，getInputStream() 每次返回全新的 ByteArrayInputStream，Filter 读完 Controller 再读零冲突。

🧪 检验理解 · Module 3 · 重点
HMAC 签名深度
1. 为什么 body 要先 MD5？
A.MD5 更安全
B.body 可能很大，MD5 压成 32 字节省 CPU，同时防篡改
C.Java 要求
D.减少日志
答案 B。几 MB body 直接 HMAC 慢，MD5 压 32 字节再 HMAC，CPU 低 100 倍。AWS SigV4 / 阿里云 OSS 通用做法。
2. 为什么 replace("+", "%20")？
A.多此一举
B.Java 把空格编 +，RFC 3986 要 %20，两端不统一签名对不上
C.性能
D.中文支持
答案 B。Java URLEncoder 实现的是 form-urlencoded（空格→+），但 RFC 3986 URI 要求空格→%20。Python/Go/PHP 大多默认 %20。不统一签名永远对不上。这一行是踩坑证明。
3. diff |= a.charAt(i) ^ b.charAt(i) 什么作用？
A.哈希
B.XOR 位累积，无论哪位不同都走完循环，避免时序差异
C.性能
D.语法
答案 B。普通 equals 字符不同立刻 return，耗时有纳秒级差。攻击者反复测量能逐位推出签名。|= XOR 累积让耗时恒定。大厂安全必考。
4. Nonce 是干嘛的？
A.让签名不一样
B.防篡改
C.防时间戳窗口内重放（配合服务端 Redis 记账）
D.无用
答案 C。只有时间戳不够——5 分钟窗口内可重发。Nonce + Redis SETNX + TTL 让每请求只生效一次。完整防重放 = Timestamp + Nonce + 服务端记账。
5. 为啥用私有内部类而不复用 PostRequestWrapper？
A.重复造轮子
B.Internal 鉴权独立业务，body 一次读到 byte[] 后两次都能读，不和 Web 链路 Wrapper 耦合
C.性能
D.随意
答案 B。独立性考虑：Internal API 鉴权不依赖 Web 登录 Wrapper 生命周期。私有内部类把 body 一次读到 byte[]，getInputStream() 每次返回新的 ByteArrayInputStream，零冲突。

定时任务 + 分布式锁

11 个 Job 里最典型的 AdqGoodsSyncJob（14k token）。配套真实的 RedisLockService——基于 Peacock 的 SharedRedisClient。

🔒真实 RedisLockService

Javaservice/RedisLockService.java（真实）
@Service
public class RedisLockService {

    @Resource(name = "sharedRedisDefaultUriList")
    private SharedRedisClient lockRedisClient;

    public static final int DEFAULT_EXPIRE_SECOND = 10;

    public Result<RedisLock> obtainLock(String lockKey) {
        return obtainLock(lockKey, DEFAULT_EXPIRE_SECOND, 0);
    }

    public Result<RedisLock> obtainLock(String lockKey, int expireSecond, int waitMilliseconds) {
        RedisLock redisLock;
        try {
            redisLock = lockRedisClient.getLock(lockKey, lockKey, expireSecond);

            if (waitMilliseconds <= 0) {
                // 非阻塞，拿不到立即失败
                if (!redisLock.tryLock()) {
                    Logs.error.error("获取 Redis Lock 失败 lockKey={} expireSecond={}", lockKey, expireSecond);
                    return BusinessCode.LOCK_TOO_FAST_ERROR.toResult();
                }
            } else {
                // 阻塞等待 waitMilliseconds
                if (!redisLock.tryLock(waitMilliseconds, TimeUnit.MILLISECONDS)) {
                    return BusinessCode.LOCK_TOO_FAST_ERROR.toResult();
                }
            }
            return BusinessCode.SUCCESS.toResult(redisLock);
        } catch (Exception e) {
            Logs.error.error("获取 Redis Lock 异常 lockKey={}", lockKey, e);
            return BusinessCode.LOCK_EXCEPTION.toResult();
        }
    }
}
📋

上一版教程写的是 redisLockService.tryExec(key, supplier) Supplier 模板。真实代码不是这样的——它返回 Result<RedisLock>，调用方自己管 lock.unlock()。这是阅文 Peacock 框架自己的封装，基于 SharedRedisClient。

🧪 检验理解 · Module 5
Job 与锁
1. obtainLock 为啥返回 Result<RedisLock> 而不是 boolean？
A.随便
B.Result 自带错误码 + 数据，上层能区分"没抢到锁"、"锁异常"、"成功"三种状态，并拿到锁对象
C.性能
D.Peacock 规范
答案 B。Peacock 的 Result<T> 包装了业务码和数据。LOCK_TOO_FAST_ERROR（没抢到锁）、LOCK_EXCEPTION（Redis 异常）、SUCCESS（拿到锁）三种状态可区分。比 boolean 信息量大。
2. Job 里为啥一定要 try...finally lock.unlock()？
A.好习惯
B.业务抛异常也必须释放锁，否则锁一直占到 TTL 自动过期，影响下次 Job
C.Java 语法要求
D.无关
答案 B。锁有 TTL 兜底（默认 10 秒），但如果业务执行 5 秒+异常，没 unlock 就要等锁过期才能下次执行。用 try-finally 确保必释放，才能快速让下一次 Job 跑（比如紧急补跑场景）。

🧵真实 AsyncTaskExecutorUtil

Javautil/AsyncTaskExecutorUtil.java（真实）
@Component
public class AsyncTaskExecutorUtil {

    @Value("${corePoolSize:16}")
    private int corePoolSize;

    private static final long KEEP_ALIVE_SECONDS = 60L;
    private static final int QUEUE_CAPACITY = 1000;

    private ExecutorService ioIntensiveExecutor;

    @PostConstruct
    public void init() {
        this.ioIntensiveExecutor = new ThreadPoolExecutor(
            corePoolSize,
            corePoolSize,            // ⭐ core == max,固定大小
            KEEP_ALIVE_SECONDS,
            TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(QUEUE_CAPACITY),
            new ThreadFactory() {
                private final AtomicInteger threadNumber = new AtomicInteger(1);
                @Override
                public Thread newThread(Runnable r) {
                    Thread t = new Thread(r, "async-io-pool-" + threadNumber.getAndIncrement());
                    t.setDaemon(true);        // ⭐ daemon 线程,JVM 退出自动终止
                    return t;
                }
            },
            new ThreadPoolExecutor.CallerRunsPolicy()  // ⭐ 反压
        );
        Logs.access.info("AsyncTaskExecutorUtil initialized: core={}", corePoolSize);
    }

    public ExecutorService getIoIntensiveExecutor() { return ioIntensiveExecutor; }

    public void submit(Runnable task) { ioIntensiveExecutor.submit(task); }

    public <T> CompletableFuture<T> supplyAsync(Supplier<T> supplier) {
        return CompletableFuture.supplyAsync(supplier, ioIntensiveExecutor);
    }
}
⚙️
3 个工业级细节

① core == max == corePoolSize：固定大小线程池，不动态扩容。避免突发流量创建大量线程耗资源。
② daemon 线程：t.setDaemon(true)。JVM 退出时守护线程自动终止，避免 Shutdown 卡住。
③ 命名 async-io-pool-N：线上 jstack / 日志一眼看出是哪个线程池的线程，排查问题关键。
④ CallerRunsPolicy：队列满时由提交任务的线程自己执行，自然反压，不丢任务。

🧪 检验理解 · Module 6
线程池
1. 为啥 core == max？
A.随便
B.固定大小池，突发流量不创建大量线程，避免资源耗尽
C.性能
D.JDK 要求
答案 B。core < max 的弹性线程池在突发流量下会创建大量新线程（每个线程 1MB 栈），容易 OOM。固定大小的好处是容量可预测，队列满时靠 CallerRunsPolicy 反压。
2. daemon 线程和普通线程区别？
A.性能更好
B.JVM 退出时 daemon 自动终止，不阻塞关闭
C.优先级高
D.无差
答案 B。普通线程（user thread）JVM 要等它执行完才能退出；daemon 线程（守护线程）JVM 会直接终止。如果线程池里的任务是可丢弃的（统计/日志），设 daemon 能让 Shutdown 快。
