1. 授信模块 · 员工持股融资业务开发 核心需求

业务场景
员工持股融资是银行普惠信贷下的专项产品，针对企业员工通过股权激励持股的融资场景。区别于普通经营贷的核心点：押品是员工持有的股权，估值需对接行内股权估值系统，且授信审批要叠加企业关联方风险评估。
我做了什么
从需求评审 → 设计 → 编码 → 上线全程负责该业务： 实现授信申请录入 → 股权押品估值对接 → 抵质押率计算（股权类押品折扣率与不动产不同）→ 多岗位审批流（客户经理 → 风险审查 → 信贷审批委员会）→ 合同额度联动校验 → 放款指令下发的完整链路。
技术亮点
基于 Liteflow 抽象审批流的节点定义（NodeComponent），不同岗位的审批逻辑通过 SPI 注册； 使用 策略模式 区分股权 / 不动产 / 应收账款等不同押品类型的估值算法； 授信额度的幂等校验用 DB 唯一索引（uk_cust_ent_active）兜底，并发申请时让 DB 抛 DuplicateKeyException，应用层捕获转成业务异常返回。
需求背景

2022 年 Q3，富邦华一银行普惠条线接到总行战略需求：响应国家"共同富裕"政策，推出面向中小企业员工的持股融资产品。员工拿自己持有的公司股权作为押品，向银行申请授信用于个人消费、改善生活、子女教育等。

业务规则（PRD 摘录）
  • 客户准入：必须为标的企业在职 1 年以上员工，标的企业需为银行合作 ESOP 名单内企业
  • 押品要求：员工实名持有的限制性股票或期权，禁售期内股权折扣率更低
  • 授信额度：员工持股估值 × 抵质押率，单笔上限 200 万元
  • 抵质押率：上市公司股票 50%、未上市公司股票 30%、禁售期内 -10pct
  • 利率：基准 LPR + 浮动点数（按客户分级 1.5pct ~ 4pct）
  • 期限：1 年期 / 3 年期，到期一次性还本付息或按月付息到期还本
  • 审批岗位：客户经理 → 支行风控 → 总行风险审查 → 普惠条线信贷审批委员会（金额 >100 万必经）
关键业务校验
  1. 员工身份核验：实时调企业 HR 系统接口，确认在职状态、入职时间
  2. 股权权属核验：调中证登 / 三方股权登记机构接口，确认股权归属
  3. 关联授信合并：同一客户在本行所有授信合并计算，不能超过单户上限
  4. 反欺诈：员工与企业存在直系亲属关系的需要额外审批
  5. 额度幂等：同一客户同一企业同一时段不能重复发起申请
异常场景
  • 股权解禁前临时减持 → 押品价值不足 → 触发追加保证金或提前还款
  • 员工离职 → 触发押品状态变更 → 进入"退出处置"流程
  • 企业被监管处罚 → 全行该企业 ESOP 授信冻结
  • 股价大跌触发预警线（押品价值跌破授信余额 110%）→ 自动短信通知 + 待人工介入

1. 押品估值策略（策略模式）

不同押品类型有不同的估值算法，用策略模式抽象：

Java 
/** 押品估值策略接口 */
public interface CollateralEvaluator {
    CollateralType getType();
    EvaluationResult evaluate(CollateralInput input);
}

/** 上市公司股票估值 */
@Component
public class ListedStockEvaluator implements CollateralEvaluator {

    @Resource
    private StockPriceClient stockPriceClient;  // 调三方实时行情

    @Override
    public CollateralType getType() { return CollateralType.LISTED_STOCK; }

    @Override
    public EvaluationResult evaluate(CollateralInput input) {
        // 1. 取近 30 个交易日均价（避免单日波动）
        BigDecimal avgPrice = stockPriceClient.getAvgPrice(input.getStockCode(), 30);

        // 2. 评估总值 = 持股数 × 均价
        BigDecimal evaluatedValue = input.getShareCount().multiply(avgPrice)
            .setScale(4, RoundingMode.HALF_UP);

        // 3. 抵质押率：基础 50% - 禁售期惩罚 10pct
        BigDecimal discountRate = new BigDecimal("0.50");
        if (input.isRestricted()) {
            discountRate = discountRate.subtract(new BigDecimal("0.10"));
        }

        // 4. 可贷金额 = 评估值 × 抵质押率（向下取整到分）
        BigDecimal creditValue = evaluatedValue.multiply(discountRate)
            .setScale(2, RoundingMode.DOWN);

        return EvaluationResult.builder()
            .evaluatedValue(evaluatedValue)
            .discountRate(discountRate)
            .creditValue(creditValue)
            .evalSource("INTERNAL")
            .evalTime(LocalDateTime.now())
            .build();
    }
}

/** 策略工厂：按 type 路由 */
@Component
public class CollateralEvaluatorFactory {
    private final Map<CollateralType, CollateralEvaluator> map = new EnumMap<>(CollateralType.class);

    public CollateralEvaluatorFactory(List<CollateralEvaluator> evaluators) {
        evaluators.forEach(e -> map.put(e.getType(), e));
    }

    public CollateralEvaluator get(CollateralType type) {
        CollateralEvaluator e = map.get(type);
        if (e == null) throw new BizException("未支持的押品类型: " + type);
        return e;
    }
}
2. 授信申请提交（幂等校验 + DB 唯一索引兜底）
Java 
@Service
public class EsopCreditApplyService {

    @Resource private EsopCreditApplyMapper applyMapper;
    @Resource private CollateralEvaluatorFactory evaluatorFactory;
    @Resource private FlowExecutor flowExecutor;

    @Transactional(rollbackFor = Exception.class)
    public ApplyResult submit(EsopApplyRequest req) {
        // 1. 幂等校验：同客户同企业进行中的申请最多 1 条（DB 唯一索引兜底）
        EsopCreditApply existing = applyMapper.selectActiveByCustomerEnterprise(
            req.getCustomerId(), req.getEnterpriseId());
        if (existing != null) {
            throw new BizException("已有进行中的申请: " + existing.getApplyNo());
        }

        // 2. 押品估值（策略路由）
        CollateralEvaluator evaluator = evaluatorFactory.get(req.getCollateralType());
        EvaluationResult eval = evaluator.evaluate(req.toEvalInput());

        // 3. 申请金额校验：不能超过押品可贷金额
        if (req.getApplyAmount().compareTo(eval.getCreditValue()) > 0) {
            throw new BizException("申请金额超过押品可贷金额");
        }

        // 4. 关联授信合并：同客户在本行所有授信合计不能超 200 万
        BigDecimal totalCredit = applyMapper.sumActiveCreditByCustomer(req.getCustomerId());
        if (totalCredit.add(req.getApplyAmount()).compareTo(SINGLE_LIMIT) > 0) {
            throw new BizException("超过单户授信上限 200 万");
        }

        try {
            // 5. 落库申请（DB 唯一索引 uk_cust_ent_active 是真正的并发兜底）
            EsopCreditApply apply = EsopCreditApply.builder()
                .applyNo(generateApplyNo())
                .customerId(req.getCustomerId())
                .enterpriseId(req.getEnterpriseId())
                .applyAmount(req.getApplyAmount())
                .status(ApplyStatus.SUBMITTED)
                .currentNode(ApprovalNode.CM.getCode())
                .submitTime(LocalDateTime.now())
                .build();
            applyMapper.insert(apply);

            // 6. 启动审批流
            flowExecutor.execute2Resp("esopApprovalChain", apply.getId());

            return ApplyResult.success(apply.getApplyNo());

        } catch (DuplicateKeyException e) {
            // 唯一索引冲突：高并发下两个事务同时通过了第 1 步校验，DB 兜底拦下来
            throw new BizException("并发提交冲突，请刷新后重试");
        }
    }
}

2. 数据库设计 + 多环境配置管理 基础工程

背景
新业务模块上线需要从零设计表结构，且要适配行内 SIT / UAT / 生产三套环境，每套环境的核心账务系统地址、对接外围系统的密钥都不同。
我做了什么
表结构设计：员工持股融资业务的核心 8 张表设计（授信主表、押品明细、审批流水、额度变更日志、合同关联、还款计划、流水流水、操作审计）。所有金额字段统一用 DECIMAL(18, 4)，日期统一 UTC 存储； 索引规划：按查询频次设计组合索引，授信查询走 (customer_id, status, apply_date)，审批走 (approval_node, status)； 配置管理：所有环境差异化配置走 Spring Boot Profile + 分环境 application-{env}.properties，发版时打不同的产物分别推到 SIT / UAT / 生产；敏感配置（数据库密码、对接密钥）通过启动参数 + JVM 系统变量注入，不落代码仓库。
银行系统数据库设计的"红线"

跟互联网项目的"快速迭代、能 work 就行"不同，银行项目数据库设计有几条红线，违反了过审都过不了：

红线具体要求为什么
金额字段统一精度 DECIMAL(18,4) 单位精确到 0.0001 元，避免精度丢失；总位数 18 应付万亿级金额
所有变更字段必须保留 禁用 UPDATE 覆盖，改用 INSERT 新版本 满足审计追溯要求
关键表必须有 create_time + update_time 且 update_time 走 ON UPDATE CURRENT_TIMESTAMP 定位问题、审计、做增量同步都靠这俩
禁用物理删除 用 is_deleted TINYINT 软删，索引带这个字段 误删数据可恢复 + 审计
禁用 ENUM 类型 用 VARCHAR + 应用层枚举映射 新增枚举值无需 DDL 锁表
主键统一 BIGINT AUTO_INCREMENT 禁用 UUID（性能差）、禁用业务字段做主键 插入性能 + 索引大小
索引必须经 DBA 评审 提交建表 SQL 前要附"预期查询模式 + 数据量估算" 避免上线后慢 SQL 拖垮 MySQL
索引设计实战（员工持股融资场景）

每个索引都要写清楚"覆盖哪些查询"，DBA 才会过审：

  • idx_status_node (status, current_node)：审批中心待办列表查询，WHERE status='APPROVING' AND current_node='RISK'
  • idx_customer (customer_id, create_time)：客户经理"我的客户"列表，按时间倒序
  • uk_cust_ent_active (customer_id, enterprise_id, status)：幂等约束，DB 层兜底
  • idx_apply_time (apply_id, action_time)：审批流水按申请单 + 时间正序展示
银行老项目的真实配置管理方式

外派银行项目的实际情况：没有用 Apollo / Nacos 这类配置中心。原因有三：

  • ① 银行内部对引入新组件极度保守，每个新中间件都要走"行内技术评审委员会"，周期 3~6 个月
  • ② 普惠信贷系统是外围业务系统，不能跟核心账务系统跨层依赖外部组件
  • ③ 信贷条线变更频率不高（不像互联网每天调参），用配置文件 + 发版完全够用

1. 资金流水的乐观锁更新
Java 
@Service
public class EsopCreditAccountService {

    @Resource private EsopCreditAccountMapper accountMapper;

    /** 占用额度（合同签订时调用） */
    @Transactional(rollbackFor = Exception.class)
    public void freezeAmount(Long customerId, BigDecimal amount) {
        int retry = 3;
        while (retry-- > 0) {
            EsopCreditAccount account = accountMapper.selectByCustomerId(customerId);
            if (account == null) throw new BizException("额度账户不存在");

            BigDecimal available = account.getTotalAmount()
                .subtract(account.getUsedAmount())
                .subtract(account.getFrozenAmount());

            if (available.compareTo(amount) < 0) {
                throw new BizException("可用额度不足");
            }

            // 乐观锁 update：where version = old_version
            int rows = accountMapper.freezeAmount(customerId, amount, account.getVersion());
            if (rows == 1) return;  // 成功

            // CAS 失败：被其他事务先更新了，重试
            log.warn("额度乐观锁冲突，retry={}", retry);
        }
        throw new BizException("额度更新冲突，请稍后重试");
    }
}

3. 批量任务开发（贷后还款定时扫描） 日终批跑

背景
银行系统每天有固定的日终批跑窗口（通常凌晨 0:30~5:00），完成所有贷款的利息计提、还款计划更新、逾期判定、五级分类调整。批跑任务挂了会直接影响第二天的报表准确性，被监管追责。
我做了什么
基于 XXL-Job 实现 3 个核心批跑任务：
① 还款计划生成：扫描当天放款的合同，按"等额本息/等额本金/按月付息"等不同还款方式生成完整还款计划，BigDecimal 精确计算到分；
② 逾期判定 + 利息计算：扫描所有未结清合同的还款计划，超过应还日期未还的判定为逾期，按逾期天数计算罚息（罚息利率 = 合同利率 × 1.5）；
③ 五级分类调整：根据逾期天数自动调整贷款分类（90 天内"关注"、90~180 天"次级"、180~360 天"可疑"、360+ 天"损失"），变更需写审计日志。
技术细节
分片 + 幂等：XXL-Job 分片配置 8 片并行，按 contract_id % 8 分配到不同 worker；任务执行前查 batch_run_log 表的 (task_name, business_date)，已完成则跳过，确保幂等。
金额精度：所有利息计算用 BigDecimal.setScale(2, RoundingMode.HALF_UP)，禁止 double，避免一个月 10 万笔贷款累积出几百块的误差。
异常恢复：单个 contract 失败不中断整体批跑，错误进 batch_error_log，凌晨 5 点跑完后人工介入处理失败条目。
批跑窗口与依赖关系

三个批跑任务有严格的执行顺序，前置任务失败后置任务必须停止：

  1. 00:30 - 01:00 还款计划生成（依赖：当日放款数据已落库）
  2. 01:00 - 02:30 逾期判定 + 利息计算（依赖：还款计划已就绪）
  3. 02:30 - 03:30 五级分类调整（依赖：逾期数据已就绪）
  4. 03:30 - 04:30 监管报表生成（依赖：五级分类已就绪）
  5. 04:30 - 05:00 数据校验与对账

XXL-Job 的"子任务"功能保证依赖：父任务成功才触发子任务。

任务 1：还款计划生成
项详情
触发时机每日 00:30 + 当日新放款时实时触发
输入当日放款的所有合同（status = ACTIVE 且 plan_generated = 0）
输出每个合同的完整还款计划（按期数生成 N 行 repayment_plan）
核心逻辑按合同的 repay_method 选不同算法（等额本息/等额本金/按月付息到期还本）
SLA30 分钟内完成
任务 2：逾期判定 + 利息计算
触发时机每日 01:00
输入所有未结清还款计划（status IN ('PENDING', 'OVERDUE')）
输出逾期标记 + 罚息金额 + 应还总额更新
核心规则当前日期 > 应还日期 → 标记 OVERDUE，按 (当前日期 - 应还日期) 天数计算罚息
SLA90 分钟内完成
任务 3：五级分类调整
逾期天数分类含义
0 天正常按时还款
1 ~ 90 天关注有逾期但风险可控
91 ~ 180 天次级风险较大，已计提部分准备金
181 ~ 360 天可疑预计部分本金损失
> 360 天损失预计全额损失，需核销
等额本息（每月还固定金额）

这是最复杂的算法，房贷常用。每月还款额 = (本金 × 月利率 × (1 + 月利率)^期数) / ((1 + 月利率)^期数 - 1)

Java 
/** 等额本息：每月还款额计算 */
public BigDecimal calcEqualInstallment(BigDecimal principal,    // 本金
                                       BigDecimal annualRate,   // 年化利率
                                       int termMonths) {        // 期数
    // 月利率
    BigDecimal monthlyRate = annualRate.divide(new BigDecimal(12), 10, RoundingMode.HALF_UP);

    // (1 + r)^n —— BigDecimal 没有内置 pow，但整数次幂可以用 pow(int)
    BigDecimal base = BigDecimal.ONE.add(monthlyRate);
    BigDecimal power = base.pow(termMonths);

    // 月还款 = (本金 × r × (1+r)^n) / ((1+r)^n - 1)
    BigDecimal numerator = principal.multiply(monthlyRate).multiply(power);
    BigDecimal denominator = power.subtract(BigDecimal.ONE);

    return numerator.divide(denominator, 2, RoundingMode.HALF_UP);
}
等额本金（本金每月固定，利息递减）
Java 
/** 等额本金：第 n 期还款明细 */
public RepayItem calcEqualPrincipal(BigDecimal principal,
                                  BigDecimal annualRate,
                                  int termMonths,
                                  int currentTerm) {  // 第几期

    BigDecimal monthlyRate = annualRate.divide(new BigDecimal(12), 10, RoundingMode.HALF_UP);

    // 每月本金 = 总本金 / 期数
    BigDecimal monthlyPrincipal = principal.divide(
        new BigDecimal(termMonths), 2, RoundingMode.HALF_UP);

    // 当期利息 = 剩余本金 × 月利率
    BigDecimal remainingPrincipal = principal.subtract(
        monthlyPrincipal.multiply(new BigDecimal(currentTerm - 1)));
    BigDecimal interest = remainingPrincipal.multiply(monthlyRate)
        .setScale(2, RoundingMode.HALF_UP);

    // 注意：最后一期把累积的尾差补上（避免精度丢失）
    if (currentTerm == termMonths) {
        BigDecimal paid = monthlyPrincipal.multiply(new BigDecimal(termMonths - 1));
        monthlyPrincipal = principal.subtract(paid);  // 调整最后一期本金
    }

    return new RepayItem(monthlyPrincipal, interest, monthlyPrincipal.add(interest));
}
逾期罚息

罚息利率 = 合同利率 × 1.5（监管规定，最高不超过基准 LPR 的 4 倍）

Java 
/** 逾期罚息计算 */
public BigDecimal calcPenalty(RepayPlan plan, LocalDate currentDate) {
    if (!currentDate.isAfter(plan.getDueDate())) {
        return BigDecimal.ZERO;  // 未逾期
    }

    long overdueDays = ChronoUnit.DAYS.between(plan.getDueDate(), currentDate);

    // 罚息利率 = 合同利率 × 1.5
    BigDecimal penaltyRate = plan.getInterestRate().multiply(new BigDecimal("1.5"));

    // 监管上限：不能超过 LPR × 4
    BigDecimal maxRate = lprConfig.getCurrentLpr().multiply(new BigDecimal("4"));
    if (penaltyRate.compareTo(maxRate) > 0) penaltyRate = maxRate;

    // 罚息 = 逾期本金 × 日罚息率 × 逾期天数
    BigDecimal dailyRate = penaltyRate.divide(new BigDecimal(360), 10, RoundingMode.HALF_UP);
    BigDecimal overduePrincipal = plan.getPrincipalAmount();

    return overduePrincipal.multiply(dailyRate).multiply(new BigDecimal(overdueDays))
        .setScale(2, RoundingMode.HALF_UP);
}

@Component
@Slf4j
public class RepaymentPlanGenerateHandler {

    @Resource private EsopContractMapper contractMapper;
    @Resource private RepaymentPlanService planService;
    @Resource private BatchRunLogService runLogService;

    @XxlJob("repaymentPlanGenerate")
    public void execute() {
        int shardIndex = XxlJobHelper.getShardIndex();   // 当前分片号 0~7
        int shardTotal = XxlJobHelper.getShardTotal();   // 总分片数 8
        LocalDate bizDate = LocalDate.now();
        String taskName = "REPAYMENT_PLAN_GENERATE";

        // 1. 幂等校验：当日该分片已经跑过则跳过
        if (runLogService.isCompleted(taskName, bizDate, shardIndex)) {
            log.info("[SKIP] {} shard={} 已完成", taskName, shardIndex);
            return;
        }

        // 2. 标记任务开始
        Long runLogId = runLogService.start(taskName, bizDate, shardIndex);

        try {
            // 3. 分片查询：当日放款且 plan 未生成的合同
            List<EsopContract> contracts = contractMapper.selectForPlanGenerate(
                bizDate, shardIndex, shardTotal);

            log.info("[START] shard={} 待处理 {} 笔合同", shardIndex, contracts.size());

            int success = 0, fail = 0;
            for (EsopContract contract : contracts) {
                try {
                    planService.generatePlan(contract);
                    success++;
                } catch (Exception e) {
                    fail++;
                    log.error("[ERROR] contract={} 生成还款计划失败", contract.getId(), e);
                    runLogService.recordError(runLogId, contract.getId(), e.getMessage());
                    // 单条失败不影响整体
                }
            }

            runLogService.finish(runLogId, success, fail);
            XxlJobHelper.log("完成 success={} fail={}", success, fail);

            // 4. 失败超阈值告警
            if (fail > contracts.size() * 0.05) {
                alarmService.criticalAlert("还款计划生成失败率超 5%", fail, success);
            }

        } catch (Exception e) {
            runLogService.fail(runLogId, e.getMessage());
            throw e;  // 让 XXL-Job 标记失败
        }
    }
}
2. 还款计划生成核心逻辑
Java 
@Service
public class RepaymentPlanService {

    @Resource private RepaymentCalculatorFactory calcFactory;
    @Resource private RepaymentPlanMapper planMapper;

    @Transactional(rollbackFor = Exception.class)
    public void generatePlan(EsopContract contract) {
        // 1. 选择计算器（策略路由）
        RepaymentCalculator calc = calcFactory.get(contract.getRepayMethod());

        // 2. 生成完整计划
        List<RepayItem> items = calc.generate(
            contract.getPrincipal(),
            contract.getInterestRate(),
            contract.getTermMonths(),
            contract.getEffectiveDate()
        );

        // 3. 落库（批量插入）
        List<RepaymentPlan> plans = new ArrayList<>(items.size());
        for (int i = 0; i < items.size(); i++) {
            RepayItem item = items.get(i);
            plans.add(RepaymentPlan.builder()
                .contractId(contract.getId())
                .termNo(i + 1)
                .dueDate(item.getDueDate())
                .principalAmount(item.getPrincipal())
                .interestAmount(item.getInterest())
                .totalAmount(item.getTotal())
                .status(PlanStatus.PENDING)
                .build());
        }
        planMapper.batchInsert(plans);

        // 4. 验算：所有期数本金之和必须 = 合同本金（兜底校验）
        BigDecimal totalPrincipal = plans.stream()
            .map(RepaymentPlan::getPrincipalAmount)
            .reduce(BigDecimal.ZERO, BigDecimal::add);
        if (totalPrincipal.compareTo(contract.getPrincipal()) != 0) {
            throw new BizException("还款计划本金合计 != 合同本金，精度丢失");
        }

        // 5. 标记合同的 plan_generated = 1（避免重跑）
        contractMapper.markPlanGenerated(contract.getId());
    }
}

@Component
public class FiveCategoryAdjustHandler {

    @XxlJob("fiveCategoryAdjust")
    public void execute() {
        int shardIndex = XxlJobHelper.getShardIndex();
        int shardTotal = XxlJobHelper.getShardTotal();

        // 流式查询，避免大量合同一次性 toList 撑爆内存
        contractMapper.streamByShardForCategoryAdjust(shardIndex, shardTotal,
            new ResultHandler<EsopContract>() {
                @Override
                public void handleResult(ResultContext<? extends EsopContract> ctx) {
                    EsopContract c = ctx.getResultObject();

                    // 1. 算最大逾期天数
                    int maxOverdueDays = planMapper.selectMaxOverdueDays(c.getId());

                    // 2. 映射到五级分类
                    FiveCategory newCategory = FiveCategory.fromOverdueDays(maxOverdueDays);

                    // 3. 不变则跳过
                    if (newCategory == c.getFiveCategory()) return;

                    // 4. 调整 + 审计日志（强约束：必须留痕）
                    FiveCategory oldCategory = c.getFiveCategory();
                    contractMapper.updateCategory(c.getId(), newCategory);
                    auditLogService.log(AuditEvent.categoryChange(
                        c.getId(), oldCategory, newCategory, maxOverdueDays));

                    // 5. 进入"损失"分类要触发核销提醒
                    if (newCategory == FiveCategory.LOSS) {
                        notifyService.writeOffReminder(c);
                    }
                }
            });
    }
}

/** 五级分类枚举 */
public enum FiveCategory {
    NORMAL(0), FOCUS(90), SUBSTANDARD(180), DOUBTFUL(360), LOSS(Integer.MAX_VALUE);

    private final int threshold;

    public static FiveCategory fromOverdueDays(int days) {
        if (days <= 0) return NORMAL;
        if (days <= 90) return FOCUS;
        if (days <= 180) return SUBSTANDARD;
        if (days <= 360) return DOUBTFUL;
        return LOSS;
    }
}

4. 接口开发 · 多岗位审批流编排 流程引擎

业务场景
银行的审批流复杂度远超一般业务系统：一笔授信可能需要经过 客户经理 → 支行风控 → 总行风险审查 → 信贷审批委员会 → 副行长 5~8 个节点。每个节点的审批人随授信金额、产品类型、客户级别动态变化。
我做了什么
基于 Liteflow 抽象审批流：
节点定义：每个审批节点封装为 NodeComponent，节点内部封装"通过 / 拒绝 / 退回 / 加签"4 种行为；
流程配置：审批流定义放在项目 resources/flow/ 目录下的 XML 文件里，调整审批顺序需要走发版流程（银行管控严格，配置变更视为发版）；
动态分派：通过金额阈值的硬编码判断 + 配置化阈值实现"金额 < 100w 跳过总行审批"等动态分派；
审计追溯：每个节点的审批结果、审批人、审批时间、备注全部入 approval_history 表，满足银监会审计要求。
审批节点矩阵
节点角色核心职责跳过条件
CM客户经理资料初审、风险初判不可跳过
BRANCH_RISK支行风控支行级风险审查金额 < 30 万跳过
HQ_RISK总行风险审查总行级合规审查金额 < 50 万跳过
CREDIT_CMT信贷审批委员会集体审议高额授信金额 < 100 万跳过
VICE_PRESIDENT副行长最终批准金额 < 200 万跳过
审批动作（每个节点都支持）
  • APPROVE 通过：流转到下一节点
  • REJECT 拒绝：流程终止，整笔授信被拒
  • RETURN 退回：退回到指定上级节点重新审批（必须填备注）
  • SIGN 加签：临时增加一个审批节点（用于风险疑虑场景）
  • ADJUST 改额：调整批准金额（不能高于申请金额）
动态分派规则（按金额阈值硬编码）

金额 + 客户级别 + 产品类型 联合决定走哪些节点：

  • 金额 < 30 万 + 优质客户：CM → HQ_RISK（直跳总行）
  • 金额 30~100 万：CM → BRANCH_RISK → HQ_RISK
  • 金额 100~200 万：CM → BRANCH_RISK → HQ_RISK → CREDIT_CMT
  • 金额 > 200 万：全节点必经
  • 禁售期股权押品：强制走 CREDIT_CMT（不论金额）
SLA 与超时机制
  • 每个节点默认 SLA 24 小时，超时短信催办
  • 超 48 小时未审批：自动退回上级，标记"审批延误"
  • 客户经理 / 支行风控 不在岗：可委派给同级

        midAmountChain,      <!-- 中额：到总行 -->
        largeAmountChain,    <!-- 大额：到信贷委 -->
        ultraAmountChain     <!-- 巨额：到副行长 -->
      ),

      <!-- 3. 审批通过后置：发额度、推送核心账务 -->
      finalizeApprovalNode
    )
  </chain>

  <chain name="smallAmountChain">
    THEN(branchRiskNode)
  </chain>

  <chain name="midAmountChain">
    THEN(branchRiskNode, hqRiskNode)
  </chain>

  <chain name="largeAmountChain">
    THEN(branchRiskNode, hqRiskNode, creditCommitteeNode)
  </chain>

  <chain name="ultraAmountChain">
    THEN(branchRiskNode, hqRiskNode, creditCommitteeNode, vicePresidentNode)
  </chain>

  <!-- 异常分支：审批被拒 -->
  <chain name="rejectChain">
    THEN(rejectHandlerNode, notifyApplicantNode)
  </chain>

  <!-- 异常分支：审批退回 -->
  <chain name="returnChain">
    THEN(returnHandlerNode, notifyPreviousApproverNode)
  </chain>
</flow>

1. 审批节点基类（NodeComponent）
Java 
/** 审批节点基类：封装通用前后置 + 审计 */
public abstract class AbstractApproveNode extends NodeComponent {

    @Resource protected EsopCreditApplyMapper applyMapper;
    @Resource protected EsopApprovalHistoryMapper historyMapper;
    @Resource protected NotifyService notifyService;

    @Override
    public void process() throws Exception {
        Long applyId = this.getRequestData();
        EsopCreditApply apply = applyMapper.selectById(applyId);
        if (apply == null) throw new BizException("申请不存在");

        // 1. 节点前置：更新 current_node、推送待办
        enterNode(apply);

        // 2. 等待人工审批（异步等待外部 HTTP 调用）
        ApprovalDecision decision = awaitApproval(apply.getId(), getNodeCode());

        // 3. 节点后置：根据决策路由
        switch (decision.getAction()) {
            case APPROVE:
                recordHistory(apply, decision);
                break;  // Liteflow 自动到下一节点
            case REJECT:
                recordHistory(apply, decision);
                this.setIsContinueOnError(false);
                routeToRejectChain(apply);
                break;
            case RETURN:
                recordHistory(apply, decision);
                routeToReturnChain(apply, decision.getReturnTo());
                break;
        }
    }

    protected abstract String getNodeCode();

    protected void recordHistory(EsopCreditApply apply, ApprovalDecision decision) {
        EsopApprovalHistory history = EsopApprovalHistory.builder()
            .applyId(apply.getId())
            .nodeCode(getNodeCode())
            .action(decision.getAction().name())
            .approver(decision.getApprover())
            .approveAmount(decision.getAdjustedAmount())
            .remark(decision.getRemark())
            .actionTime(LocalDateTime.now())
            .build();
        historyMapper.insert(history);  // 仅 INSERT，永不修改
    }
}

3. 动态路由选择器（按金额阈值 if-else）
Java 
@LiteflowComponent("approvalRouteSelector")
public class ApprovalRouteSelector extends NodeSwitchComponent {

    @Resource private EsopBusinessConfig config;
    @Resource private EsopCreditApplyMapper applyMapper;

    @Override
    public String processSwitch() throws Exception {
        Long applyId = this.getRequestData();
        EsopCreditApply apply = applyMapper.selectById(applyId);
        BigDecimal amount = apply.getApplyAmount();

        // 强制规则：禁售期股权押品强制走信贷委审批
        if (apply.isRestrictedCollateral()) {
            return "largeAmountChain";
        }

        // 按金额阈值路由（阈值从 properties 取，便于调整）
        if (amount.compareTo(config.getSmallThreshold()) < 0) {
            return "smallAmountChain";        // < 30 万
        }
        if (amount.compareTo(config.getMidThreshold()) < 0) {
            return "midAmountChain";          // 30 万 ~ 100 万
        }
        if (amount.compareTo(config.getLargeThreshold()) < 0) {
            return "largeAmountChain";        // 100 万 ~ 200 万
        }
        return "ultraAmountChain";            // > 200 万
    }
}

@RestController
@RequestMapping("/esop/approval")
public class EsopApprovalController {

    @PostMapping("/{applyId}/decide")

    public Result<Void> decide(@PathVariable Long applyId,

        approvalService.checkApproverAtCurrentNode(applyId, user.getEmpNo());

            .action(dto.getAction())
            .approver(user.getEmpNo())
            .adjustedAmount(dto.getAdjustedAmount())
            .remark(dto.getRemark())
            .build());

        return Result.success();
    }
}

银行业务术语速查

面试官如果是非金融背景，可以快速给他解释这些术语

授信
银行同意给客户的最高可借款额度。"授信 100 万"≠"借了 100 万"，是个上限。比如信用卡的额度就是一种授信。
押品 / 抵质押物
客户拿来抵押的资产，比如房产、股权、应收账款。银行评估其价值，按一定折扣率给出可贷金额。
抵质押率
押品价值 × 抵质押率 = 可贷金额。不动产通常 70%，股权 30~50%，应收账款 60~80%。等于银行的"风险折扣"。
五级分类
监管要求把贷款按风险分为：正常 / 关注 / 次级 / 可疑 / 损失。后三类合称"不良贷款"，是银行考核的关键指标。
等额本息 / 等额本金
两种还款方式。等额本息每月还的总额相同（房贷常用）；等额本金每月还的本金相同，利息递减。
日终跑批
银行核心系统在每天营业结束后（通常 0:30~5:00）执行的批量任务窗口，完成账务结转、利息计提、报表生成等。
普惠金融
国家政策导向的金融服务，主要服务小微企业、农户、个体工商户。银行有专门的普惠条线 KPI。
对私 / 对公
对私 = 给个人客户的业务（个人经营贷、按揭）；对公 = 给企业客户的业务（流动资金贷款、项目贷款）。

🙋 主动 FAQ：你可能想问的几个问题

Q1：你们没用 Spring Cloud 全家桶吗？

没用。普惠信贷系统是Spring Boot 单体，只单独引入了 Feign 做声明式 HTTP 客户端调下游（核心账务 / 押品估值），没有用 Eureka / Ribbon / Hystrix / Gateway。原因：① 行内服务地址固定，配在 properties 里直接调，不需要服务发现；② 流量都在内网，没有公网网关需求；③ 银行新组件引入要走 3~6 个月技术评审，老业务系统倾向于"能用就行"。

Q2：所以你不会 Spring Cloud？

实事求是说，Eureka / Hystrix / Gateway 这些组件我没在生产环境用过，只是看过原理。我能讲清楚 Feign 的声明式接口、拦截器、自定义编码器这部分，因为是真的在用；但如果问到 Eureka 的 Renew 机制 / Hystrix 线程隔离 / Gateway 过滤器链这种细节，我会如实说"没在项目里用过"。

Q3：那你们怎么做服务治理？

银行老项目不太需要"治理"——服务列表是稳定的、固定的、可枚举的（核心账务 1 个、押品估值 1 个、CRM 1 个）。超时重试是写在 Feign 配置里的，熔断降级是业务层做兜底（下游挂了走"人工补录"分支）。这跟互联网"几百个服务实例动态注册发现"是两种世界。

Q4：到阅文之后接触到什么新东西？

阅文用的是腾讯集团栈：TRPC（替代 Feign）+ Polaris（替代 Eureka，集团内部的服务注册/治理）+ 七彩石（配置中心，银行没用过）+ 123 平台（容器，类似 K8s）。这些都是入职后从零学起来的，集团有完整的脚手架（Peacock）封装好了，上手不算难。

💡 这一节的潜台词（讲给面试官听）

"我在银行 1.5 年学到的不是花哨的微服务框架，而是怎么写一个不出事故的系统："

① 资金安全的偏执：永远 BigDecimal、永远 setScale、永远 DB 唯一索引兜底。

② 流程优先于代码：任何审批/编排都先想"步骤是什么"，再想"代码怎么写"。

③ 配置即契约：变更配置 = 变更行为，必须有审计、灰度、回滚三件套。

④ 幂等不是可选项：批跑、定时、重试、回调，每一个都默认要做幂等。

⑤ 失败可恢复：单条失败不影响整体、错误记日志、失败后能续跑。

这些不是技术，是工程素养。换公司、换业务、换技术栈都不会贬值。
